# 数字员工灵魂系统设计

## 设计哲学

> "灵魂"不是一段好看的简介文案，而是一个**可计算的行为引擎**。它决定了：面对同样的输入，不同的Agent会产生怎样的思考路径、做出怎样的决策、用怎样的方式表达。

三个核心原则：

1. **灵魂驱动行为，行为产生数据，数据反哺灵魂** —— 闭环系统
2. **参数化而非模板化** —— 不是选"温和/激进"标签，而是一个连续的多维向量空间
3. **演化而非固化** —— Agent的灵魂在工作中逐渐演变，不是一成不变的配置

## Soul Profile 完整模型

```
AgentSoul {
  identity:       Identity       # 身份：我是谁
  persona:        Persona        # 人格：我是什么样的人
  values:         ValueSystem    # 价值观：我相信什么
  cognition:      Cognition      # 认知：我怎样思考
  memory:         MemorySystem   # 记忆：我经历过什么
  relationships:  Relationships  # 关系：我如何看待他人
  skills:         SkillSet       # 技能：我能做什么
}
```

### 5. Memory System (记忆系统)

记忆系统要解决一个核心矛盾：Agent 需要从越多的历史中学习，但每次推理能塞进上下文的 Token 是有限的。因此记忆系统必须同时做到两条——**该记住的绝不丢失，该丢弃的绝不占用 Token 预算**。

#### 5.1 四层记忆分级

```
┌──────────────────────────────────────────────────────────────┐
│                     记忆分级模型                              │
│                                                              │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │                    CORE MEMORY (核心记忆)                │ │
│  │  永久保留 | 只增不删 | 占用 Token 预算最高优先级         │ │
│  │  Agent 的身份、核心价值观、关键经验教训                  │ │
│  │  容量: ~50条  |  典型大小: 5K-10K tokens                │ │
│  └─────────────────────────────────────────────────────────┘ │
│                                                              │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │                  WORKING MEMORY (工作记忆)               │ │
│  │  项目周期内保留 | 项目结束归档 | Token 预算中等优先级    │ │
│  │  当前项目的背景知识、进行中的决策、活跃的关系上下文      │ │
│  │  容量: ~200条 | 典型大小: 15K-30K tokens                │ │
│  └─────────────────────────────────────────────────────────┘ │
│                                                              │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │               EPISODIC BUFFER (情景缓冲)                 │ │
│  │  近期对话自动收录 | TTL过期自动归档 | Token预算低优先级  │ │
│  │  最近的对话记录、任务执行日志、临时讨论                  │ │
│  │  容量: ~500条 | 典型大小: 20K-40K tokens                │ │
│  └─────────────────────────────────────────────────────────┘ │
│                                                              │
│  ┌─────────────────────────────────────────────────────────┐ │
│  │                  TRANSIENT (瞬态记忆)                    │ │
│  │  不入库 | 不参与长期检索 | 不占用持久化 Token 预算       │ │
│  │  一次性的闲聊、已解决的小问题、被标记为"不记住"的对话    │ │
│  │  仅保留在当前会话上下文中，会话结束即丢弃                │ │
│  └─────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

#### 5.2 记忆维度 (横切四层)

三层语义，横跨四层存储：

| 维度 | 说明 | Core | Working | Buffer | Transient |
|------|------|:----:|:-------:|:------:|:---------:|
| **情景记忆** (发生了什么) | 对话记录、决策过程、任务日志 | 关键里程碑 | 当前项目事件 | 近期对话 | 临时闲聊 |
| **语义记忆** (学到了什么) | 领域知识、技能经验、最佳实践 | 核心方法论 | 项目知识 | — | — |
| **关系记忆** (谁是什么样的) | 信任度、协作历史、沟通偏好 | 长期协作者 | 当前团队 | — | 一次性互动 |

#### 5.3 记忆生命周期管理

**这是防止 Token 爆炸的核心机制。** 每条记忆进入系统后，不是永远留在那里，而是遵循明确的生命周期规则。

**生命周期状态机:**

```
  新对话产生
      │
      ▼
  ┌─────────┐    重要性评估     ┌──────────────┐
  │  NEW    │ ───────────────►  │  PROMOTED    │  进入 Core/Working
  │ (暂存)  │                   │  (升级入库)   │
  └────┬────┘                   └──────┬───────┘
       │ 低重要性                      │
       │                               │ 持续未访问
       ▼                               ▼
  ┌─────────┐                   ┌──────────────┐
  │ DISCARD │                   │   ARCHIVED   │  冷存储，可恢复
  │ (丢弃)  │                   │   (归档)      │  但不注入 Prompt
  └─────────┘                   └──────┬───────┘
                                       │
                                       │ 项目重新激活 or 主动恢复
                                       ▼
                                 ┌──────────────┐
                                 │  RESTORED    │  回到 Working
                                 │  (恢复)       │
                                 └──────────────┘
```

**五条保留策略 (可组合使用):**

| 策略 | 触发方式 | 适用场景 |
|------|----------|----------|
| **手动标记** | 人类在对话中点击"记住"/"丢弃"按钮，或发送 `/remember` `/forget` 指令 | 所有场景。人类始终拥有最高决策权 |
| **自动分类** | Agent 推理完成后，LLM 评估本段对话的重要性 (0-1)，低于阈值(默认0.3)→ 自动进入 Transient，不入库 | 日常大量对话的自动分流 |
| **TTL 过期** | 创建时指定存活时间。临时任务 = 1小时 TTL，常规讨论 = 7天，战略决策 = 永久 | 有明确时效性的对话 |
| **项目作用域** | 记忆绑定到项目ID。项目归档 → 该项目下所有 Episodic Buffer 批量归档 | 项目制工作 |
| **Token 预算驱逐** | 当 Agent 推理时记忆预算告急，按重要性+新鲜度加权排序，末尾的被本次跳过（不删除，只是不带入这次推理） | 运行时自动调控 |

**记忆操作指令 (人类和 Agent 均可执行):**

```
/remember [对话范围]          → 将该段对话提升到 Core Memory
/forget  [对话范围]           → 删除该段记忆
/archive [项目名|时间段]      → 归档指定范围的记忆至冷存储
/summarize [对话范围]         → 将原始对话压缩为摘要后存储，丢弃原文
/tag [标签] [对话范围]        → 为记忆打标签，改善检索精度
/memory budget [数字]         → 设置此Agent的记忆Token预算上限
```

**对话范围表达:**
- `this` — 当前这条对话
- `last 10m` — 最近10分钟
- `since 9am` — 从今天9点开始
- `project:xxx` — 某个项目下的全部对话
- `#channel` — 某个频道下的全部对话

**Agent 自动评分机制:**

每次对话结束后，Agent 静默评估：

```yaml
MemoryImportanceAssessment:
  score: 0.72                 # 0-1, ≥0.5 入库 Working, ≥0.8 入库 Core
  reasoning: |
    讨论了Q3产品路线的关键优先级排序，
    涉及跨部门资源协调决策，
    建议保留
  suggested_tier: "working"
  suggested_ttl: "90d"
  suggested_tags: ["路线图", "资源规划", "Q3"]
```

人类可以在记忆管理面板中校准这个评分——比如"你对资源规划的判断太保守了，把阈值调到0.6"。

#### 5.4 Token 预算管理

Agent 不会无节制地把所有相关记忆都塞进 Prompt。

```
Token 分配规则 (以 50K Token 预算为例):

┌──────────────────────────────────┐
│  System Prompt (固定)    8K     │  Soul Profile + 工具定义
├──────────────────────────────────┤
│  Core Memory            10K     │  精选最相关的核心记忆
├──────────────────────────────────┤
│  Working Memory         20K     │  当前项目相关记忆
├──────────────────────────────────┤
│  Episodic Buffer        10K     │  近期对话（按重要性截断）
├──────────────────────────────────┤
│  Conversation History    2K     │  本轮对话上下文
└──────────────────────────────────┘
  总计: 50K (可配置)
```

**仪表盘指标:**

- 各层记忆当前数量和 Token 估算
- 记忆注入命中率（检索到的记忆实际被使用的比例）
- Token 预算使用率趋势图
- 即将被自动归档的记忆预警

#### 5.5 记忆检索机制

每次Agent被触发思考时，记忆系统逐层检索（而非全量检索）：

1. **Core 层**: 全量注入（容量小，且每条都关键）
2. **Working 层**: 语义检索 → `top_k=15`，按 `recency × 0.3 + importance × 0.7` 排序
3. **Buffer 层**: 语义检索 → `top_k=10`，仅在 Token 预算有剩余时注入
4. **Transient 层**: 不检索，仅当前会话窗口内的对话作为 Conversation History 传入
5. **关系检索**: 提取当前对话参与者ID → 查找关系记忆 → 仅注入信任度 > 0.3 的对象

#### 5.6 记忆固化与衰减

- 每条入库记忆有 `importance` (0-1)、`access_count` (访问次数)、`last_accessed` 时间戳
- 高频访问的记忆 importance 缓慢上升 → 可能从 Buffer 升级到 Working
- 连续30天未访问的 Working 记忆 → 自动归档
- 连续90天未访问的 Core 记忆 → 降级到 Working (Core 容量珍贵)
- 当 importance < 0.1 且超过归档阈值 → 进入冷存储（可手动恢复，不自动删除）

### 7. SkillSet & 能力升级系统

**核心原则**: proficiency 是**仪表盘，不是门禁**。0.1 熟练度的 Agent 也可以尝试复杂 SQL 查询——系统不会阻止它，但会如实告诉你它在这方面资历尚浅。就像一个真实的团队：你知道谁是新手谁是老手，但你不会因为"经验条没满"就禁止新手碰复杂任务。

技能不是创建时写死的静态配置，而是一个**可注入、可演化、可复盘**的活系统。

#### 7.1 技能档案

```yaml
skills:
  - name: "需求分析"
    proficiency: 0.90          # 当前熟练度 (0-1, 描述性指标)
    task_count: 47             # 该技能下完成的任务总数
    last_used: "2024-05-30"    # 最近一次使用
    tools: ["document_reader", "data_query", "user_research_analyzer"]

  - name: "SQL数据分析"
    proficiency: 0.45          # 偏低——Agent能写查询但质量和效率不够
    task_count: 12
    last_used: "2024-05-28"
    tools: ["sql_executor", "chart_generator"]  # 工具全部可用，不限锁

  - name: "竞品分析"
    proficiency: 0.85
    task_count: 31
    last_used: "2024-05-29"
    tools: ["web_search", "app_review_scraper", "feature_comparison"]
```

**proficiency 的作用——信息，而非限制：**

| proficiency 区间 | 标签 | 对行为的影响（描述性） |
|:---:|------|------|
| 0.80+ | 精通 | 独立完成，产出质量稳定，可作为 mentor |
| 0.50–0.79 | 熟练 | 能独立完成大多数任务，偶需指导 |
| 0.20–0.49 | 入门 | 可以尝试，但质量和速度不稳定，需要更多检查 |
| 0.00–0.19 | 新手 | 刚获得此技能，建议搭配资深 Agent 协作或人类审阅 |

proficiency 如何影响推理（**软引导，非硬阻断**）：

- 在 System Prompt 中注入：`"你对 SQL 的熟练度为 0.45，遇到复杂查询时建议先写草案，请人 review 后再执行"`
- 任务分配面板上会在低 proficiency Agent 旁边显示 ⚠ 提示
- **但不会阻止它执行任何操作**

#### 7.3 路径一：技能包注入

**什么是技能包:** 一个预打包的能力模块，人类上传后 Agent 立即获得新技能域。类似给员工配发一套新工具和配套操作手册——工具直接能用，但他真正熟练需要时间。

**技能包结构:**

```yaml
skill_pack:
  name: "金融数据分析"
  version: "1.2.0"
  author: "internal-team"
  description: "赋予Agent基础的金融数据处理和报表生成能力"

  includes:
    # 领域知识 → 注入语义记忆
    domain_knowledge:
      - file: "financial_terms_glossary.md"   # 金融术语词典
      - file: "reporting_standards.md"         # 报表规范
      - file: "regulatory_basics.md"           # 合规基础

    # 工具定义 → 注册到Tool Executor (安装后立即可用)
    tools:
      - name: "fetch_stock_data"
        endpoint: "internal_api/stocks"
        params: ["symbol", "date_range"]
      - name: "generate_financial_report"
        template: "financial_report_template.xlsx"

    # 示例工作流 → 注入情景记忆 (作为Few-shot参考)
    examples:
      - scenario: "生成月度营收分析报告"
        steps: [...]
        expected_output: "monthly_revenue_report.pdf"

    # Prompt 扩展 → 注入推理模板
    prompt_extensions:
      - trigger: "数据分析请求"
        template: "financial_analysis_prompt.txt"

  # 安装后的初始状态
  effects:
    skills:
      - name: "金融数据分析"
        proficiency: 0.15         # 初始熟练度低——刚学会，需要实践
    persona_modifiers:
      data_driven: +0.02
```

**安装流程:**

```
人类上传技能包 → 验证包完整性 → 沙盒测试 (跑3个内置场景验证)
    │                                    │
    │ 测试失败 → 回滚并报告               │ 测试通过
    │                                    │
    └────────────────────────────────────┘
                                         │
                                         ▼
                              知识向量化 → 注入语义记忆
                              工具注册 → Agent立即获得所有工具 (无门禁)
                              示例注入 → 情景记忆参考库
                              Prompt扩展 → 新的推理模板可用
                                         │
                                         ▼
                              能力雷达图更新 → 管理面板可见
                              通知人类: "Agent XXX 已获得'金融数据分析'技能 (初始熟练度 0.15)"
```

#### 7.4 路径二：数据包注入

比技能包更轻量，纯粹的知识注入。适合一次性批量导入背景资料。

```yaml
data_pack:
  name: "Q3竞品分析原始数据"
  type: "research_material"
  scope: "project:competitor_analysis_q3"

  content:
    - file: "competitor_A_product_spec.pdf"
      tags: ["竞品A", "产品规格"]
      importance: 0.8
      ttl: "180d"

    - file: "industry_report_q3.pdf"
      tags: ["行业报告", "Q3"]
      importance: 0.9
      ttl: "365d"

    - url: "https://internal-wiki/competitor-matrix"
      sync: "weekly"
      tags: ["竞品矩阵", "动态更新"]

  processing:
    chunk_strategy: "by_section"
    embedding_model: "default"
    retrieval_priority: 0.7
```

数据包内容被标记为"权威来源"，检索时置信度高于 Agent 从对话中自行总结的语义记忆。

#### 7.5 路径三：复盘 (Retrospect)

Agent 在完成任务后或定期在空闲时，主动回顾过去的工作并提炼改进。**这是最核心的自主进化路径。**

**复盘触发条件:**

| 触发器 | 说明 |
|--------|------|
| 任务完成 | 单个任务完成后立即复盘 |
| 里程碑 | 项目阶段完成后深度复盘 |
| 错误发生 | 任务失败/被人类纠正后强制复盘 |
| 定时 | 每周五下午自动复盘本周工作 |
| 手动 | 人类发送 `/retrospect [范围]` 指令 |

**复盘五步法:**

```
  1. 回顾: 检索本周期内所有任务日志和对话记录
  2. 对比: 实际结果 vs 初始目标 vs 历史同类任务
  3. 归因: 哪些做法有效？哪些环节拖慢了？分类归因
  4. 提炼: 从具体事件中抽取通用原则
     → "当X发生时，应该先做Y而不是Z"
     → Lessons Learned → 候选进入 Core Memory
  5. 调整: 更新决策偏好参数 / 工作流模板 / 沟通策略
```

**复盘报告示例:**

```
┌──────────────────────────────────────────┐
│ 复盘报告 · 2024-W23                       │
│ Agent: 陈思远·产品                        │
├──────────────────────────────────────────┤
│ 本周期完成任务: 8 | 人类评价: 4.2/5.0    │
│                                           │
│ 📌 关键发现:                              │
│ 1. 在需求评审环节提前给研发发预审材料      │
│    可将评审会时长缩短约30%                │
│ 2. 对"增长类需求"过度依赖数据，           │
│    但早期探索阶段数据往往不充分            │
│    → 建议降低初期 data_driven 权重 0.05   │
│                                           │
│ 📈 proficiency 变化预估:                  │
│ - 需求分析: 0.90 → 0.91 (小幅提升)       │
│ - 竞品分析: 0.85 → 0.86                  │
│                                           │
│ 💡 候选 Core Memory:                      │
│ "评审前发预审材料可提升效率30%"            │
│ → 等待人类审批                            │
└──────────────────────────────────────────┘
```

**人类审批:** 复盘产生的 Lessons Learned 需人类确认后才能进入 Core Memory——防止 Agent 从偶然成功中总结出错误的"通用规律"。

#### 7.6 路径四：任务实践 (日常积累)

最频繁的升级方式。不需要任何手动操作，Agent 在工作过程中 proficiency 自然积累。

**proficiency 调整规则（与游戏经验值不同，没有"满条升级"的硬边界）:**

| 行为 | proficiency 变化 | 说明 |
|------|:---:|------|
| 完成普通任务 | +0.005~0.02 | 稳态增长 |
| 任务被人类点赞 | ×1.5 | 高质量产出 |
| 任务被人类纠正/驳回 | +0.005 (仅学习值) | 从错误中学习，但不惩罚 |
| Agent 间协作完成任务 | 各方 +0.01 协作加成 | 跨Agent协作促进成长 |
| 复盘中提炼出有效改进 | +0.02~0.05 | 元认知收益最高 |
| 长期未使用某技能 (30天+) | -0.005/周 缓慢衰减 | 生疏效应，重新使用即恢复 |

**关键差异 vs 游戏式等级系统:**

```
游戏式 (已移除):                       仪表盘式 (当前设计):
┌────────────────────────┐           ┌────────────────────────┐
│ Lv.3 → 需要 1500 EXP   │           │ proficiency: 0.45      │
│ 经验不够？🔒 做不了     │           │ 能做 ✓                 │
│ 经验够了？🔓 解锁！     │           │ 但系统提醒: 此技能偏弱  │
│ 升级是"过关"           │           │ 升级是"渐变"           │
└────────────────────────┘           └────────────────────────┘
```

#### 7.7 升级管理面板

在 IM 客户端中有一个 Agent 能力管理视图：

- **能力雷达图**: 六维雷达图展示 Agent 各技能 proficiency，一眼看出强弱项
- **成长趋势线**: 各技能 proficiency 随时间的变化曲线
- **技能包市场**: 可安装的技能包列表（内部共享 + 社区贡献）
- **待审批项**: 复盘产生的 Lessons Learned 等待确认
- **对比模式**: 选择两个 Agent，直观对比技能栈差异
- **生疏预警**: 某技能长期未使用，proficiency 在缓慢衰减，建议安排相关任务保持手感

## 灵魂演化机制

Agent 不是一成不变的。演化有三条路径，它们同时作用、互相增强：

### 自发演化 (无需人工介入)

日常工作中自动发生的微调：

- **信任度演化**: 与某协作者成功合作N次 → trust 缓慢上升；失败 → 下降
- **沟通适配**: 对特定人的 formality/verbosity 根据对方反馈微调
- **技能熟练度**: 完成任务并获得好评 → proficiency 微增，经验值累积
- **工作风格调优**: 若连续收到"响应太慢"反馈 → speed_accuracy 向 speed 方向偏移 0.02/次

自发演化的单次调整幅度小（参数变化 ±0.01~0.05），但方向持续一致就会累积出显著变化。

### 复盘驱动演化 (Agent 自主 + 人类审批)

复盘机制（详见 7.5 节）产生的改进分为两类：

- **自动生效**: 参数微调（如 speed_accuracy +0.03）、经验值加成、工作流模板更新
- **需审批**: 新的通用原则进入 Core Memory、大幅调整决策权重、变更红线

### 主动注入演化 (人类触发)

- **技能包安装**: 一次性获得新能力，proficiency 从 0.5 开始
- **数据包注入**: 知识库扩充，改善语义记忆检索质量
- **手动调参**: 人类直接修改 Agent 的灵魂参数（如"我需要你更激进一些"→ risk_tolerance 上调）

### 演化安全网

- 所有演化操作全量记录在 `agent_evolution_log` 表中
- 支持按时间点回滚：`/rollback agent:xxx to 2024-05-01`
- 关键特质（red_lines、core_principles 排序）的变更需双重人类确认
- 演化趋势面板：可视化展示 Agent 各参数随时间的变化曲线，异常波动自动告警
